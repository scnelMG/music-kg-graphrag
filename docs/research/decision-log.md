# Research Decision Log

Access date for all sources: 2026-07-01.

| Decision | Selected option | Alternatives | Evidence | Tradeoff | Impact on implementation |
| --- | --- | --- | --- | --- | --- |
| Canonical music identity | MusicBrainz MBIDs | Spotify IDs, Discogs IDs, title/artist strings | MusicBrainz API supports core entities, search/lookup/browse, MBIDs, JSON/XML, and one-call/sec rules: https://musicbrainz.org/doc/MusicBrainz_API | Coverage gaps for obscure/Korean indie releases remain. | Add source-qualified external IDs and manual override/unknown states. |
| Cover art source | Cover Art Archive | Spotify images, Discogs images, manual upload | Cover Art Archive is keyed to MusicBrainz release/release-group resources: https://coverartarchive.org/ | Some releases lack art. | Cover lookup runs after MBID candidate selection and can return missing-cover. |
| Tag/similarity enrichment | Last.fm optional | MusicBrainz tags only, Spotify genres | Last.fm API and terms: https://www.last.fm/api/intro and https://www.last.fm/api/tos | Requires API key and crowd data can be noisy. | Store tags as soft evidence with source/provenance, not canonical truth. |
| Public knowledge enrichment | Wikidata optional | Wikipedia scraping, no enrichment | Wikidata is CC0 and provides linked-data/WDQS access with access etiquette: https://www.wikidata.org/wiki/Wikidata:Data_access | WDQS is not for fuzzy/broad scans. | Use QIDs for known entities and scoped enrichment only. |
| Primary graph DB | Ontotext GraphDB | Neo4j, Apache Jena Fuseki, Amazon Neptune | GraphDB supports RDF/SPARQL, inferencing, RDF formats, connectors, and enterprise deployment paths: https://graphdb.ontotext.com/documentation/11.0/ | Requires local GraphDB service and license/version documentation. | Todo 1 uses GraphDB service; Todo 12 loads RDF and runs SPARQL snapshots. |
| Neo4j role | Comparison/future extension | Primary graph DB | Neo4j has GDS and GraphRAG ecosystem docs: https://neo4j.com/docs/neo4j-graphrag-python/current/ | Native model is property graph, not RDF/OWL/SHACL first. | Mention in docs; do not design MVP ontology around Cypher. |
| Fuseki role | Lightweight fallback/test reference | Primary graph DB | Apache Jena Fuseki is a SPARQL server: https://jena.apache.org/documentation/fuseki2/ | Less complete enterprise GraphDB portfolio story. | Keep RDF/SPARQL standards portable; do not depend on Fuseki-specific behavior. |
| Cloud graph DB | Defer | Amazon Neptune primary | Neptune supports RDF/SPARQL and property graph APIs but is managed AWS infrastructure: https://docs.aws.amazon.com/neptune/latest/userguide/intro.html | Cost/account complexity hurts local reproducibility. | Use Docker/local services first; document cloud path later. |
| Ontology standard | RDF/OWL with SHACL validation | Property graph only, JSON only | RDF triples: https://www.w3.org/TR/rdf11-concepts/; OWL overview: https://www.w3.org/TR/owl2-overview/; SHACL: https://www.w3.org/TR/shacl/ | More modeling overhead than plain tables. | Todo 5 must define TTL ontology and SHACL shapes before graph loading. |
| Vector search | pgvector in PostgreSQL | Qdrant, Pinecone, FAISS-only | pgvector provides vector search inside Postgres: https://github.com/pgvector/pgvector | Less specialized than a dedicated vector DB at scale. | Store MVP embeddings in PostgreSQL; defer external vector DB. |
| Recommendation method | Graph path + vector hybrid with transparent ranking | Neural KG recommender, popularity, pure LLM | KGAT/KGCN/RippleNet show KG relations help recommendation: https://arxiv.org/abs/1905.07854, https://arxiv.org/abs/1904.12575, https://arxiv.org/abs/1803.03467 | Lower benchmark ambition, higher auditability. | Implement rule/query ranking first and return evidence paths. |
| Explanation contract | Faithful graph/vector evidence only | Post-hoc prose explanation | Explainable recommendation survey and path reasoning papers: https://arxiv.org/abs/1804.11192, https://arxiv.org/abs/1906.05237 | Requires stricter no-evidence handling. | API responses include evidence paths, source IDs, and insufficient-evidence fallback. |
| GraphRAG scope | Retrieve graph paths + vector snippets, then generate | General chatbot, arbitrary text-to-SPARQL | RAG and GraphRAG papers/docs: https://arxiv.org/abs/2005.11401, https://arxiv.org/abs/2404.16130, https://microsoft.github.io/graphrag/ | Narrower question set. | Later GraphRAG endpoint must cite retrieved graph paths and refuse unsupported answers. |
| Notion sync stance | Dry-run, non-destructive, conflict-aware | Treat Notion as source DB, overwrite freely | Notion page/data-source properties, update semantics, and rate limits: https://developers.notion.com/reference/page, https://developers.notion.com/reference/patch-page, https://developers.notion.com/reference/request-limits | More sync state and conflict logic. | Preserve existing Notion schema/values; add sync job state and dry-run payloads. |
| Evaluation stance | Small offline and qualitative evidence evaluation | Claim model accuracy | KGQA generalization caution: https://arxiv.org/abs/2205.06573; explainable recommendation survey: https://arxiv.org/abs/1804.11192 | Cannot oversell recommender quality. | Docs and tests must cover no-evidence, explanation coverage, and fixture leave-one-out examples. |
| Music-domain ontology grounding | Reuse music KG patterns from Polifonia/Music Meta/DOREMUS | Generic graph schema from recommender papers only | Polifonia PON: https://link.springer.com/chapter/10.1007/978-3-031-47243-5_17; Music Meta: https://archives.ismir.net/ismir2023/paper/000102.pdf; DOREMUS: https://www.researchgate.net/publication/327711083_DOREMUS_A_Graph_of_Linked_Musical_Works_17th_International_Semantic_Web_Conference_Monterey_CA_USA_October_8-12_2018_Proceedings_Part_II | More ontology research up front, but avoids a toy album-only graph. | Todo 5 should keep metadata/review/provenance core and document deferred modules for instruments, performances, and symbolic score features. |
| Symbolic music scope | Defer MusicXML/melodic feature KG | Include score-level graph in MVP | MusicXML KG construction with SPARQL Anything: https://oro.open.ac.uk/85326/1/Music_Knowledge_Graphs_Paper%20%283%29.pdf | Less impressive musicology scope, but keeps MVP aligned to personal album records. | Ontology should not require score data; future extension note is enough. |
| Korean/indie source handling | MusicBrainz + Discogs core, others enrichment/availability | Spotify-first catalog lookup | Localized source pass found MusicBrainz/Discogs stronger for non-mainstream identity and physical editions; Spotify is availability only. | Discogs adds source complexity if used early. | Add manual review, aliases/transliterations, and source-specific provenance. |
